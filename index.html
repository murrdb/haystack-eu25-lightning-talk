Hi, I'm Roman. I maintain Metarank, it's an open-source reranker, LambdaMART, the usual. And for years I had this itch. You send it 500 candidates, it pulls a hundred features per document, runs the model. Model, ten milliseconds, nice. Whole request, two hundred. So where did the other 190 go? Redis. And I picked Redis because Redis is fast, right? Yeah. One GET is fast. Five hundred documents times a hundred fields is a totally different sport.

Poor Man's Feature Store

features built offline in batch, served online from Redis, the model waits on both

This is Metarank, and honestly every ranker I've seen. Telemetry comes in, a batch job turns it into features, the fresh ones land in Redis. A request comes in, the ranker pulls features for every candidate, runs the model. The model is the small box. The fetch is where the request goes to die.

More Candidates, More Waiting

Metarank, same model, more candidates: the feature fetch dominates

Models get faster every year. This line doesn't care. It's linear in candidates, because every candidate is a feature fetch. You want depth 500 for recall, you pay 500 lookups, every request. And every new feature makes the slope steeper.

And it gets worse when you look at which features. Query stuff, document stuff, few keys, hot, fine. Then the interaction ones. This user with this query. This document for this query. That's a product. I pulled real numbers from my day job at Delivery Hero yesterday, restaurant ranking. Vendor, query and customer features together: under ten percent of the rows we store. Interaction features, customer-times-vendor and friends: the other ninety. Now one day of traffic. Ninety-nine percent of the customer-times-vendor keys the ranker asked for did not exist. And of the customer-times-vendor rows we do store, that day touched five percent. A week, a quarter. And in the query-times-vendor table half the cells are null, the conversion columns are 90 percent null. Now put that in Redis as hashes. Every row is a hash with fifteen named fields in RAM, nulls included, cold or not. Feast-based store, materialized from BigQuery, HSET layout, textbook. The data layer costs almost four times more than the ranker it feeds. And there's no knob to turn, it's the layout, you can't fix it without redesigning the whole thing.

murrdb: Redis for Batch Reads

keys + columns in, Arrow IPC out, zero-copy into pandas/torch

engine layout RAM p50, Rust p50, Python e2e

100M rows × 10 float32, 1000 keys per read · github.com/murrdb/murr-benchmark

So, side project. Murrdb. Looks like Redis, but for batch reads. You send keys and column names, you get Apache Arrow back over HTTP. Only the columns you asked for, and Arrow drops straight into pandas or torch. No parsing. Look mom, zero copy. On a hundred million rows it's three times faster than a Redis blob and twelve times faster than the hash thing, and in Python the gap gets wider because there's nothing left to decode. Confession: version zero was an Arrow HTTP wrapper I vibe-coded in two days, and it burned 90 percent of CPU inside arrow compute. Those kernels are great at scanning a billion rows and terrible at fetching a thousand. So now storage is boring row-wise RocksDB, and Arrow lives only on the wire.

Hot in RAM. Cold on S3. Nulls Free.

RAM capped at 2 GiB, 100M rows murr Postgres
p50, 1000 keys × 10 cols 6.3 ms 189 ms
  • ROADMAPSlateDB backend: nodes hold no state
  • ROADMAPsparse columns: empty cell = 0 bytes
That's the latency half. Now the bill. Hot data in RAM, warm on NVMe, everything else on S3. I capped it at two gigs of RAM and it still answers in six milliseconds. Postgres with the same cap, two hundred. The trick is that NVMe is embarrassingly parallel: ten thousand reads at queue depth 256 is four milliseconds, not a second. Two things are not shipped yet, roadmap tag, don't quote me. SlateDB as the backend, so a node holds zero state and scaling down at night is just killing pods. And sparse columns, empty cell, zero bytes. That one's the actual fix for the ninety-one percent.
